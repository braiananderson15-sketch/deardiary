Implementation plan

Make Dear Diary a passive habit with an explicit workflow.

Move the “when should I journal?” decision into durable harness guidance. Keep the installed skill focused on how to record or recall an entry, and extend setup to manage the connection safely.

Status: proposed Scope: CLI + skill + tests Default: global guidance

Target outcome

One policy, one workflow, one safe installer.

Every supported harness sees a concise passive reminder on each run. When the reminder fires, the agent loads the Dear Diary skill and follows a stable MCP-first workflow. Re-running setup repairs drift without duplicating text or overwriting unrelated user instructions.

Responsibility split

Keep the trigger separate from execution.

1

AGENTS / CLAUDE guidance

Decides when a situation is diary-worthy and asks the agent to invoke the skill.

→
2

Dear Diary skill

Chooses record or recall, shapes the entry, and applies voice and fallback rules.

→
3

MCP / CLI

Performs durable local storage and scoped reads through the existing interfaces.

Global by default

Dear Diary spans projects, so normal setup installs user-level passive guidance. Project guidance remains an explicit option because it may become tracked team policy.

Managed blocks

Own only the stable marked block and its single preceding separator newline. Preserve all surrounding content, formatting, file permissions, and unrelated harness settings.

Implicit activation stays on

The passive instruction must be able to hand work to the skill. Do not make the skill user-only while setup depends on agent-directed activation.

Initial boundaries

Keep the first release deliberately narrow.

  • Manage passive guidance for Codex and Claude only; retain existing OpenCode MCP setup, but do not guess an unverified global instruction path.
  • Do not maintain a registry of every repository ever configured. Project setup and removal always target the repository containing the current directory.
  • Do not add hooks, automatic end-of-turn logging, or background diary writes.
  • Do not copy the full passive trigger policy back into SKILL.md.

Proposed CLI contract

Extend setup instead of adding another lifecycle command.

deardiary setup [--check] [--yes] [--guidance <global|project|none>]

--guidance global   Manage user-level passive guidance (default)
--guidance project  Manage guidance at the current Git repository root
--guidance none     Install MCP and skills without touching passive guidance

deardiary uninstall [--level <integrations|cli|full>] [--yes]
                    [--guidance <global|project>]

--guidance global   Remove managed user-level guidance (default)
--guidance project  Remove managed guidance from the current Git repository
  • --check evaluates exactly the selected guidance scope.
  • --yes applies the previewed default deterministically.
  • project fails before writes when the current directory is not in Git.
  • none leaves any previously installed guidance untouched.
  • Uninstall removes only the selected guidance scope; it does not search other repos.
  • Setup reports that open harness sessions must restart before new guidance loads.

Canonical passive policy

Keep the pointer compact but sufficient.

Generate harness-specific invocation wording around one shared policy. The managed content should carry the trigger; the skill should not repeat it. 

<!-- deardiary:start -->

## Dear Diary

When work reveals a blocker that cost meaningful effort, a reusable win,
or an actionable observation worth carrying forward, invoke $deardiary at
the next natural pause. Also invoke it when the user asks to recall diary history.
<!-- deardiary:end -->

Use the native skill spelling for each harness. Keep marker syntax stable across versions so setup, check, repair, and uninstall share one ownership boundary.

Implementation sequence

Five cuts, each independently verifiable.

Phase 1Define the model

Add guidance scope and resolved paths

  • Add a GuidanceScope union: global | project | none.
  • Extend lifecycle paths with global Codex and Claude guidance candidates; resolve CODEX_HOME rather than assuming ~/.codex.
  • Resolve the Git root only for project scope. For Codex, plan the durable AGENTS.md target and also plan an existing non-empty AGENTS.override.md so the managed policy is not shadowed.
  • Resolve Claude guidance through a harness-specific target, not a shared guess.
  • Represent every guidance change as the existing previewable file-plan shape.
Phase 2Manage blocks safely

Implement deterministic insert, replace, inspect, and remove

  • Insert the canonical block once. Own one separator newline immediately before the start marker in non-empty files so the marker stays structurally independent and removal restores the original bytes exactly.
  • Replace a complete older block in place and report it as drifted.
  • Reject malformed or duplicate marker pairs before any file is written.
  • Preserve unrelated bytes and retain the current atomic write and backup behavior.
  • Remove only the managed insertion; delete the file only if it becomes empty.
Phase 3Wire lifecycle UX

Integrate setup, check, doctor, and uninstall

  • Add guidance plans beside MCP and skill plans in setup previews.
  • Show CURRENT, MISSING, or DRIFTED in setup checks.
  • Teach doctor to identify missing guidance or incomplete override coverage.
  • Remove managed guidance at the existing integrations uninstall level, using the uninstall command's explicit guidance scope.
  • Keep the all-or-nothing preflight: one unsafe target prevents every planned write.
Phase 4Tighten the skill

Make SKILL.md an execution workflow

  • Narrow the description to explicit requests or active instructions calling for Dear Diary.
  • Remove setup maintenance and the duplicated “when to write” policy.
  • Keep MCP-first tool selection, CLI fallback discovery, voice, and examples.
  • Validate the packaged skill and refresh copied skill fixtures through setup tests.
Phase 5Document and release

Explain the behavior where users encounter it

  • Update command help and README setup/uninstall examples.
  • Describe global default, project opt-in, and none escape hatch.
  • Call out restart requirements and managed-block ownership.
  • Run package tests, typecheck, build, and a temporary-home CLI smoke test.

Test matrix

Prove preservation and idempotence first.

Fresh files

  • Create global guidance with canonical content.
  • Create project guidance only when explicitly selected.
  • Leave no partial files when confirmation is declined.

Existing files

  • Preserve unrelated instructions byte-for-byte.
  • Create non-clobbering backups before updates.
  • Preserve file permissions during atomic replacement.

Drift and damage

  • Repair one outdated canonical block.
  • Reject unmatched or duplicate markers before writes.
  • Report shadowed global guidance clearly.

Repeatability

  • A second setup produces no changes or backups.
  • setup --check exits zero only when selected scope is current.
  • Skill and guidance upgrades drift independently.

Uninstall

  • Remove only the managed insertion.
  • Retain a user-owned file with remaining content.
  • Remove an installer-created file when it becomes empty.
  • Remove only the selected global or current-project scope.

Scope safety

  • Honor CODEX_HOME and temporary HOME fixtures.
  • Reject project mode outside Git.
  • Never resolve a write target to a broad directory.

Risks and controls

Protect user-authored instructions.

Risk Control
Setup duplicates guidance on every run. Stable markers plus exact canonical comparison.
A malformed marker causes content loss. Fail the full preflight; write nothing until every target is safe.
Global guidance is installed but shadowed. Plan the durable base file and an existing active override as one setup unit.
Project setup changes team policy unexpectedly. Require explicit --guidance project and preview the repository path.
The skill and guidance restate different thresholds. Keep trigger policy only in guidance; keep execution only in the skill.

Definition of done

The change is complete when all outcomes are observable.

  • Normal setup previews and installs global passive guidance.
  • Project guidance requires an explicit scope.
  • Setup is idempotent and repairs canonical drift.
  • Malformed managed blocks stop all writes safely.
  • Check and doctor report guidance health accurately.
  • Scoped uninstall preserves every byte outside the managed insertion.
  • The skill contains workflow mechanics, not passive trigger policy.
  • CLI help and README match implemented behavior.
  • Lifecycle, parser, CLI, typecheck, and build validations pass.
  • A fresh harness session can follow guidance into the installed skill.
